# 建模先行合法，provider 先行仍禁（ADR 0002 的窄例外）

**状态**：已决（2026-11-12）。本 ADR **不放宽** 0002，只把「模型」与「provider」分开，给出可机械判定的分界。

## 背景

0002 定的是「先有客户再实现 provider，不为想象的接口写 provider」。这条纪律挡住了为想象接口造通用 HTTP provider 的冲动，是对的。

但 ERP 板块要回答「每个子模块有没有」——覆盖矩阵的 21 格必须逐格定态。而「定态」这件事本身要求先有**模型**：库存得有 SKU/批次/仓库这些对象类型，采购得到货得有事件类型，估值得有科目与算法规则。这些模型在客户到来之前就必须存在，否则矩阵只能写「不知道」，客户连「你要接什么」都问不出来。

于是就产生一个表面矛盾：全覆盖要求先建模，0002 要求先有客户。二者冲突的错觉来自把「模型」和「provider」当成同一类东西。

## 决定

**为想象业务建模合法；为想象接口写 provider 仍禁。**

分界是可判定的，不是措辞：

| | 模型（本板块） | provider（连接器仓） |
|---|---|---|
| 是什么 | 我们自己的类型系统：事件类型、对象类型、过账规则 | 别人系统的契约：动作面、鉴权形态、字段映射 |
| 谁定义 | 我们 | 对方（SDK / OpenAPI / 官方文档） |
| 错了谁承担 | 我们自己改类型 | 客户接不通，且我们无法解释"接通了"是什么意思 |
| 登记处 | `fd-erp/shared/coverage-matrix.json` 的模型缺口 | 本仓 `gaps.json` 的 provider 缺口 |
| 判据 | 事件类型注册表 / 对象类型 / 规则表里有没有 | 目录动作面 / 角色候选集 / 执行器测试计数 |
| 何时可做 | 随时（建模先行） | 锚点客户确认品牌与接口形态之后 |

## 后果

- 矩阵里 `needs_onboarding` 格的 blocker 必须写清缺的是哪一类：缺模型缺口还是 provider 缺口。**两类互换判红**（`fd-erp/tools/check_coverage_matrix.py` 与 `erp-connector-onboarding` 的「缺口两分类」条款）。
- 建模先行**不构成接通**。矩阵里「库存数量面已交付」（内核能力）与「WMS provider 无」是两件事，必须分别陈述，MUST NOT 用前者暗示后者。
- 0002 的全部禁令原样有效：不新增通用 HTTP/Webhook provider，不让凭证里取 base URL，不为想象品牌立 provider 目录条目。
- 若某个模型建完之后长期没有客户（比如生产制造的对象模型），它应当被降级或移除，而不是无限期挂在矩阵里充数——这是矩阵复核窗口的作用。

## 复核

- 触发复核：本仓 `gaps.json` 出现第 5 类缺口，或出现「模型已建但无客户」超过两个复核窗口的能力。
- 裁决来源：`openspec/specs/erp-board/spec.md`「覆盖边界与建模先行」+ `erp-board-coverage` 四态条款。
