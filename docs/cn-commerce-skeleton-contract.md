# 国内电商平台接入骨架契约（实现挂起）

状态：**骨架先行，实现挂起**。锚点客户的平台范围（淘宝/天猫/京东/其他）与接口形态确认前，
本仓不新增国内电商 provider（决策见 `docs/adr/0002-no-generic-http-provider.md`）。

消费方：ERP 线跨境电商连接器包的 `cn-commerce-store` 绑定（`provider: "cn-commerce"`,
`providerRole: true`, `allowOperations: ["read"]`, `optional: true`）。角色形态意味着目录里
不需要同名 provider，客户在连接器卡片选定平台与账号；但平台本身必须先作为一个 provider 存在。

**已知畸形面**：拼多多上游接口 schema 缺失，因此在 ERP 侧连绑定都**不声明**（声明了就是一条
永远关不上的缺口）。本骨架不为拼多多留槽位；上游 schema 补齐后另议。

## 载体

- `src/providers/<platform>/` 全新目录（一平台一 provider，不做"一个 provider 服务所有平台"——
  各平台的授权形态、签名、限流、字段都不同，混在一起会让 `allowOperations` 失去约束对象）；
- 凭证形态按平台实际：淘宝/天猫系为 OAuth（`TOP` 网关 + session key）；京东为 app key + 签名；
- **禁止**从凭证/入参取 base URL（ADR 0002 理由 1）；端点代码字面量。

## 动作面骨架（全部 `operationType=read`）

1. **订单查询**（`list_orders`）：按店铺 + 时间窗拉订单（订单号、下单时间、金额、状态、
   退款标记），支持分页与增量（按 `modified` 时间）。
2. **结算/账单查询**（`list_settlements`）：平台结算账单（账期、应结、扣费、实结）——
   与订单面是**两个面**，金额不可能靠订单相加得到（佣金、运费险、活动补贴都在结算侧）。
3. **店铺信息查询**（`get_shop`）：店铺 id、名称、币种、账期口径。

## Trigger 骨架

**订单/退款事件**：支持消息服务的平台用 webhook（验签 + 幂等）；否则 poll（按 `modified`
增量）。事件面至少覆盖：订单创建、订单支付、退款成功。

## 验收判据（一轮闭环）

> 账期结算单读回 → 与订单面交叉验证 → 差额可解释

1. 某账期的 `list_settlements` 合计 = 该账期 `list_orders` 合计 − 平台扣费 − 退款 + 补贴，
   差额为零或可逐项归因；
2. 增量拉取不重不漏（同一 `modified` 窗口重复拉取结果幂等）；
3. 有 trigger 时：一笔退款事件落记录（验签、幂等、伪造拒收）。

## 形态确认后的分支

- **平台开放 API**：按骨架实现；
- **只给后台导出**（部分平台仅提供账单 CSV）：走 ERP 线既有导出文件通道，不在本仓实现；
- **需要浏览器自动化抓后台**：`browser_use` 等 provider 的 read 动作是**自家会话管理**，
  不是"代读任意后台"——此路径不通，须先评估专用 provider（同 ADR 0002 理由 3 的边界）。

## 前置依赖（ERP 线挂账）

锚点客户实际开店的平台清单与优先级、各平台开发者资质与凭证发放、账期口径
（确认收货 vs 结算日）。确认前，ERP 侧该绑定报 `unmapped`，状态面如实显示。
