# 商家电商 ERP 接入骨架契约（实现挂起）

状态：**骨架先行，实现挂起**。国内商家的订单/库存/结算三腿最集中的来源是电商 ERP
（旺店通 / 聚水潭 / 管家婆一类），而不是逐个平台直连：平台直连各有一套 OAuth/签名，
且多数平台不开放库存面；**国内三方对账缺库存腿就不成立**，所以这条通道优先。

消费方：`fd-erp-vertical-templates` 的 `connectors/merchant_erp.py`（已就位，provider
名由 `ERP_MERCHANT_ERP_PROVIDER` 指定，默认 `merchant_erp`）。

## 载体

- 目录里按**厂商**立案：`src/providers/<vendor>/`（如 `wangdiantong`、`jushuitan`），
  不做一个 `merchant_erp` 大 provider 服务所有厂商——各家的授权形态、签名、字段都不同，
  混在一起会让 `allowOperations` 失去约束对象（ADR 0002 已就这一点做过裁决）。
- 首次落地用哪家由锚点客户决定；`merchant_erp` 只是模板侧的默认占位名。
- 厂商字段差异走**配置映射**（字段别名表 + 状态码映射），不为每家复制一套适配器。

## 凭证形态

- API key + secret（多数厂商），签名方式按厂商实现，端点字面量；
- 凭证由连接器运行时持有（BYOK），模板层不读；
- 授权失败 → `AUTH_FAILED`，不得降级成空列表。

## 动作面骨架（全部 `operationType=read`）

1. `list_orders`：按店铺 + 时间窗，含平台单号、支付时间、金额、币种、状态、退款标记；
   支持游标分页与按 `modified` 增量。
2. `list_settlements`：结算/账单（账期、应结、扣费、实结）。**不是订单加总**：
   佣金、优惠、运费险只在结算侧。
3. `list_inventory`：SKU × 仓库维（可用、锁定、在途）。这是国内对账唯一可靠的库存腿。
4. `get_shop`：店铺 id、平台归属（淘宝/天猫/京东）、币种、账期口径。

频控：厂商普遍按分钟级限流；触发返回 429 → 运行时 `RATE_LIMITED`，退避重试有上限。

## 验收判据（一轮闭环）

> 账期结算单读回 → 与订单面交叉验证 → 差额可解释

1. 某账期 `list_settlements` 合计 = 订单合计 − 平台扣费 − 退款 + 补贴，差额为零或可归因；
2. 库存腿能对到订单扣减（在途单打 `needs_explanation=logistics`，不自行判定物流因果）；
3. 增量拉取幂等（`stable_id` 集合一致），翻页到 `hasNextPage=false` 才算读完。

## 矩阵与对外口径

- 任一厂商未实现：`merchant_erp.*` 保持 `unmapped`，原因「通道未实现；国内库存腿的唯一来源」；
- 实现后仍未真实读取：仍 `unmapped`，原因改「动作已落地，缺真实读取记录」；
- 结算面是否可得取决于**厂商是否开放账单面**：不开放时矩阵 `settlements` 记 `unmapped`，
  报表与对账显式标缺腿，绝不用订单金额推算结算额。

- 厂商开放平台资质与 API key 发放；
