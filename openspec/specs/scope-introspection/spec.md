# scope-introspection Specification

## Purpose
给消费侧一面只读镜子，回答两个它无法自行判断的问题：这次调用为什么被拒（该申请什么范围），以及某个 provider 在目录里到底覆盖不覆盖我声明的那几类操作——目录知识因此只留在连接器一侧，消费侧不必复制也不该复制目录。

## Requirements

### Requirement: 按动作 id 解释拒绝原因

平台 SHALL 提供租户侧只读查询：给定一个 `actionId`，以调用令牌自身的策略求值，返回该动作的 `provider`、`operationType`、是否放行、拒绝时的错误码与未命中的策略层（允许/拒绝规则的来源与模式）。

查询 SHALL 只对调用令牌可见的目录与租户信息作答：MUST NOT 返回其他租户的连接存在性，MUST NOT 因为查询本身而执行任何动作或产生计费。

查询 SHALL 在动作 id 不在目录中时明确区分「未知动作」（404）与「已知但被拒」（200 + 不允许判定），使消费侧不会把拼写错误渲染成授权入口。

#### Scenario: 解释范围不足

- **WHEN** 以范围 PAT 查询一个被动作白名单挡下的动作 id
- **THEN** 返回该动作的 provider 与 operationType，判定为不允许，并指明未命中动作白名单

#### Scenario: 解释部署级屏蔽

- **WHEN** 查询的动作被部署级策略屏蔽
- **THEN** 返回判定为不允许并指明拒绝来源为部署层，消费侧据此不提供「去授权」（授权也无法越过部署级管控）

#### Scenario: 未知动作与拒绝可区分

- **WHEN** 查询的 actionId 不在目录中
- **THEN** 返回 404 未知动作，不返回「被拒」判定

#### Scenario: 查询不产生副作用

- **WHEN** 反复查询同一动作
- **THEN** 不执行该动作、不写运行记录、不改变任何令牌状态

### Requirement: 按 provider 与操作类回答目录覆盖

平台 SHALL 提供租户侧只读查询：给定 `provider` 与操作类集合（读/写），返回该 provider 在目录中的覆盖情况——每类操作是否存在可执行动作、可执行的时动作数量，以及缺口类目。

该查询 SHALL 用于消费侧判定「包声明的外部面能否被目录兑现」：provider 不在目录、或某类操作在目录中完全不可执行时，消费侧据此把绑定标为「目录缺口」而不是「用户未配置」。

查询 MUST NOT 修改目录、MUST NOT 需要 provider 的凭证、MUST NOT 触发任何外部调用（纯目录判定）。

#### Scenario: 覆盖完整

- **WHEN** 查询一个读写动作齐备的 provider 的读与写两类
- **THEN** 两类均报告覆盖，并给出各类动作数量

#### Scenario: 写面缺口

- **WHEN** 查询某 provider 的写类而目录中该 provider 只有只读动作
- **THEN** 写类报告缺口（覆盖为否、动作数为零），读类正常报告覆盖

#### Scenario: provider 不在目录

- **WHEN** 查询的 provider 不存在于目录
- **THEN** 明确返回未知 provider（404），消费侧据此区分「目录没有这个系统」与「有这个系统但能力不够」

#### Scenario: 纯目录判定

- **WHEN** 查询一个尚未建立任何连接的 provider
- **THEN** 查询照常返回覆盖情况，不需要凭证、不发起外部调用
